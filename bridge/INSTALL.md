# claw-remote · install & distribution

This document covers how to build a distributable tarball of the
`claw-remote` daemon and how to install it on a host (server, laptop or
embedded device). For day-to-day development, use the workspace flow
(`npm --prefix bridge run dev`) instead.

## Targets supported

The build pipeline produces one tarball per `<os>-<arch>`:

| Target | Build command | Notes |
|---|---|---|
| `darwin-arm64` | `scripts/build-tarball.sh` (host) | Apple Silicon |
| `darwin-x64` | `scripts/build-tarball.sh --target darwin-x64` | Intel Macs |
| `linux-x64` | `scripts/build-tarball.sh --target linux-x64` | Most VPS, x86_64 SBCs |
| `linux-arm64` | `scripts/build-tarball.sh --target linux-arm64` | Raspberry Pi 4/5 (64-bit), AWS Graviton |
| `windows-x64` | `scripts/build-tarball.sh --target windows-x64` | Windows 10/11 with PowerShell |

The bundled daemon is a single CommonJS file (`lib/start.cjs`) generated by
`tsup` with everything bundled except native addons (`better-sqlite3`,
`ssh2` optional helpers). The native bits ship in `node_modules/` with the
correct prebuilt binary for the target, downloaded by `prebuild-install`.

## Build pipeline

```
scripts/build-tarball.sh [--target <os>-<arch>] [--version <ver>] [--out <dir>]
```

Steps:

1. Bundles `src/bin/start.ts` via `tsup.dist.config.ts` (CJS, Node 20, sourcemap).
2. Writes a `package.json` stub pinning the two native deps.
3. Runs `npm install --omit=dev` inside the staging dir with
   `npm_config_target_platform` / `npm_config_target_arch` set, so
   `prebuild-install` fetches the right `better_sqlite3.node`.
4. Tars the staging dir into `out/claw-remote-<os>-<arch>-<version>.tar.gz`.

Cross-target builds rely on prebuilts being available upstream. If
`prebuild-install` falls back to building from source, you need the matching
toolchain on the build host. In practice the prebuilts cover all five
canonical targets.

A successful run prints:

```
[build-tarball] target=linux-x64 version=0.1.0
[build-tarball] building dist with tsup (externals: better-sqlite3, ssh2)
[build-tarball] installing runtime deps for linux-x64
[build-tarball] wrote /path/to/out/claw-remote-linux-x64-0.1.0.tar.gz
```

## Installer

`scripts/install.sh` is a POSIX `sh` script — runs on Alpine, BusyBox and
the macOS shell shipped by Apple. It does not assume `bash`.

Common flows:

```sh
# Local tarball into ~/.local/claw-remote with launchd auto-start (mac)
./scripts/install.sh \
  --tarball ./out/claw-remote-darwin-arm64-0.1.0.tar.gz \
  --launchd

# Remote download + systemd --user unit (Linux VPS)
curl -fsSL https://example.com/install.sh | sh -s -- \
  --tarball https://example.com/claw-remote-linux-x64-0.1.0.tar.gz \
  --systemd

# Custom ports
./scripts/install.sh --tarball ./out/...-0.1.0.tar.gz --systemd \
  --bridge-port 9778 --http-port 9779

# Dry install (no service registration)
./scripts/install.sh --tarball ./out/...-0.1.0.tar.gz --no-start

# Uninstall everything (prefix + symlink + service unit)
./scripts/install.sh --uninstall
```

Defaults:

- prefix: `$HOME/.local/claw-remote`
- bin symlink: `$HOME/.local/bin/claw-remote`
- systemd unit: `$HOME/.config/systemd/user/claw-remote.service`
- launchd plist: `$HOME/Library/LaunchAgents/com.claw.remote.plist`
- bridge port: `24112`, http port: `24113`

The install is idempotent: the previous prefix is moved aside and replaced
atomically (`<prefix>.prev`), and the symlink is overwritten.

## Remote install via SSH (`ssh.installBridge`)

Once a host is registered in the mesh as a `linuxServer` peer with SSH
credentials, the daemon can push the binary to it without leaving the
WebSocket bridge. The flow:

1. Mac client sends a frame:
   ```json
   {
     "kind": "request",
     "id": "r-install",
     "payload": {
       "method": "ssh.installBridge",
       "hostId": "vps-1",
       "localBinaryPath": "/path/to/claw-remote-linux-x64-0.1.0/bin/claw-remote",
       "remotePath": "/usr/local/bin/claw-remote",
       "port": 24112,
       "httpPort": 24113
     }
   }
   ```
2. The daemon opens an SSH session (via `@clawjs/ssh-client`), uploads the
   binary via SFTP, `chmod 755`, writes the systemd unit (or a custom
   `unitBody` if provided), runs `systemctl --user daemon-reload` and
   `enable --now`.
3. Audit event: `proxySsh` / `success` with `context.method=ssh.installBridge`.

To install via this path you should upload the whole tarball, not just the
wrapper, since the wrapper alone is useless without `lib/` and
`node_modules/`. The common pattern is:

- Upload the tarball with `ssh.sftp.writeFile`.
- Extract on the remote with `ssh.exec`: `tar xzf /tmp/clawjs.tgz -C /opt`.
- Run `install.sh` over `ssh.exec`.

A future iteration will combine these into a single `ssh.installBridge`
call that wraps tarball upload + extraction + service registration.

## Troubleshooting

| Symptom | Diagnosis |
|---|---|
| `node not found in PATH` when running the wrapper | The bundled wrapper assumes `node >= 20`. Install Node or set `NODE=/path/to/node` in the systemd `Environment=` line. |
| `Cannot find module 'better-sqlite3/build/Release/better_sqlite3.node'` | The prebuilt did not match the host. Re-run `scripts/build-tarball.sh --target <correct-target>` or run `npm rebuild better-sqlite3` inside the install prefix. |
| `EADDRINUSE 127.0.0.1:24112` | Another `claw-remote` (or `clawix-bridged` legacy Swift) holds the port. Stop it or change `CLAW_REMOTE_PORT`. |
| systemd unit not autostarting | `systemctl --user status claw-remote.service` — usually missing `loginctl enable-linger $USER` on Linux servers. |
| install.sh exits with `tarball not found` | Path is wrong or download failed; pass `--tarball` with an absolute path or a reachable URL. |
| Mac daemon doesn't survive reboot | Make sure `--launchd` ran and the user is logged in at boot; for headless servers use `sudo launchctl` + `/Library/LaunchDaemons/`. |
